## 1. 全局约定

| 项 | 约定 | 说明 |
|---|---|---|
| 路径前缀 | `/api` | 前端 `get('/xxx')` 经 baseURL `/api` 拼接；`vue.config.js` 的 pathRewrite 会去掉前缀，后端 `ApiPrefixFilter` 自动补回，两种写法均可用（已实测） |
| 响应结构 | `{ code: 200, message: "OK", data: ... }` | 成功码 **200**（不是 0）；前端 `request.js` 判定 `res.data.code === 200` |
| 失败响应 | `{ code: 501/4xx/5xx, message, data: null }` | 未登记接口返回 **code:501**，不再像旧 `backend_` 那样静默 200 + null |
| 金额单位 | 元，DECIMAL(10,2) | 不是「分」；前端仅做展示格式化 |
| 视频 ID | `vid` 数字（BIGINT） | 不是 `videoId` 字符串 |
| 商品 ID | `p1`~`p10` 字符串 | 两端已对齐 |
| 分页 | `page` 从 1、`size` 默认 20 | 返回值含 `total` |
| 认证 | `Authorization: Bearer <JWT>`，TTL 7200s | 当前为宽松模式：无 token 时按 uid=1 处理（便于联调），上线前须改为强制校验 |
| 验证码 | `123456`（严格校验） | 手机端旧逻辑「任意 6 位数字即登录成功」必须删除 |
| 时间 | `yyyy-MM-dd HH:mm:ss` / 展示用字符串 | 契约字段以各接口样例为准 |
| 编码 | UTF-8 | `spring.sql.init.encoding=UTF-8` 已显式设置，避免 Windows GBK 乱码 |

`request.js` 按开关分流 mock / 真实 axios，并补齐 `put()` / `del()` 对应本服务的 `PUT|DELETE /cart/{id}`。

按前端源码中全部 `get()/post()` 字面量路径逐个打真实请求（模板变量路径映射为样例值）：

| 指标 | 结果 |

**边界**：暂未开放入口一律保留；不做任何前端持久化（点赞 / 收藏 / 关注 / 分享不落 localStorage）；手机端仍为纯 mock，未接 API 层；本轮验证为构建 + 全量 SFC 编译 + 接口运行时冒烟 + 静态检查，**未做浏览器实测**。

详见 `交付文档/pilipili前后端对接与问题整改解决方案.html` 第九节。

## 9. 异常与错误码规范

取自 `common/ErrorCode.java`，**不新增自定义码**；客户端只看到规范化 `{code, message, data:null}`，不返回堆栈或内部细节。

| code | 枚举 | 触发条件 | 前端应如何处理 |
|---|---|---|---|
| 200 | `SUCCESS` | 正常 | 读 `data` |
| 400 | `PARAM_ERROR` | 必填缺失 / 类型错 / 越界（如 `POST /cart` 缺 `productId`、`register` 缺 `username`） | 展示 `message`，**不重试** |
| 401 | `UNAUTHORIZED` | 未登录 / token 过期 | 触发刷新 token 流程，仍失败则拉起登录 |
| 403 | `FORBIDDEN` | 越权访问他人资源 / 管理端角色不足 | 展示无权限提示，**不重试** |
| 404 | `NOT_FOUND` | 资源不存在（失效 vid、无此商品） | 落提示页，不空白 |
| 409 | `CONFLICT` | 资源冲突（如 `POST /mall/order/create` 购物车无已选商品） | 展示 `message`，刷新列表 |
| 500 | `SYSTEM_ERROR` | 未捕获异常 | 通用文案 + **最多自动重试 3 次**；`fetch` 失败显示离线提示 |
| 501 | `NOT_IMPLEMENTED` | **端点未登记/未迁移**（`contract_seed` 里也没有） | 联调期视为漏接口，必须清零；上线前不得存在 |

前端约定：**4xx 不重试、5xx 自动重试最多 3 次、网络失败显示离线提示**；`request.js` 已在开发态对 `code!=200` 留痕，后续可把错误映射为统一友好提示。

### 9.1 HTTP 状态恒为 200（最容易踩坑的一条）

`common/Result.java` 与 `common/GlobalExceptionHandler.java` 的注释已明确：**所有 `/api/**` 响应的 HTTP 状态码恒为 200，业务状态只由 body 里的 `code` 区分。**

原因：PC 端 `src/network/request.js` 与全部页面采用 `.then(res => res.data.code === 200)` 写法。若后端按常规 REST 返回 HTTP 400/404/500，axios 会直接 reject 进 `catch`，现有页面逻辑全部失效——这是后端迁移时**第一优先级**要守住的约定。

因此后端**禁止**使用 `@ResponseStatus`、`ResponseEntity.status(...)`、`ResponseStatusException`、`sendError()` 表达业务失败；一律走 `Result.fail(...)` 或抛 `BusinessException`。`code:0` 是 v2 蓝图的写法，v1 不采用。容器级错误（静态资源、网关超时）不在此约束内，但 `/api/**` 已由 `ApiController` 的 `@RequestMapping("/api/**")` 统一兜住。

### 9.2 异常分类与处理链（照现有 4 个 `@ExceptionHandler`）

| 异常 | 抛出位置 | 处理器 | 输出 code | 日志级别 |
|---|---|---|---|---|
| `BusinessException(ErrorCode, detail)` | **Service 主动抛**（如商品不存在、加购缺参、购物车空） | `handleBusiness` | 该枚举的 code + 自定义 detail | WARN |
| `MethodArgumentNotValidException` | Bean Validation（引入 DTO 后生效，当前未启用） | `handleValidation` | 400 + 拼接的字段错误信息 | 建议 WARN |
| `NoHandlerFoundException` | 真正未映射的路由 | `handleNotFound` | 404 | WARN |
| `Exception`（兜底） | 任何未捕获异常：SQL 异常、NPE、JSON 解析失败、超时 | `handleUnknown` | 500 + 通用文案 | ERROR（带堆栈，**仅服务端日志**） |

**501 的来源要说清**：它不是异常处理器产生的，而是 `ContractDispatcher.dispatch()` 找不到精确端点、路径模式也匹配不上、`SeedRepository.find()` 也无记录时，主动抛 `BusinessException(NOT_IMPLEMENTED)`。与 404 的区别是「路径已被 `/api/**` 收进来，但没有登记任何处理器或契约种子」。这条 WARN 日志是迁移看板的数据源。

### 9.3 异常场景矩阵

| 场景 | code | 后端行为 | 前端行为 |
|---|---|---|---|
| 缺必填 / 类型错 / 越界 | 400 | 边界校验后 `BusinessException(PARAM_ERROR, 具体原因)` | 展示 `message`，不重试 |
| 资源不存在（失效 vid、无此商品） | 404 | `BusinessException(NOT_FOUND)` | 落提示页，不空白 |
| 未登录 / token 过期 | 401 | 收紧鉴权后由 `JwtInterceptor` 拦截 | 刷新 token，仍失败则拉起登录 |
| 越权访问他人资源 / 角色不足 | 403 | 按 token 内 uid 判定，不信请求参数 uid | 无权限提示，不重试 |
| 状态冲突（订单无已选商品、非法流转、库存不足） | 409 | `BusinessException(CONFLICT)` | 展示 `message` 并刷新列表 |
| **幂等重放**（重复收藏/关注/加购） | **200** | 不报错，返回首次成功结果，不产生第二条（见 11.2） | 正常渲染 |
| 事务失败 / DB 不可用 / 未捕获异常 | 500 | **整段回滚**，禁止返回半成品 `data`；不泄漏 SQL、表名、堆栈给客户端 | 通用文案 + 最多重试 3 次 |
| 端点未迁移 | 501 | `ContractDispatcher` 抛出；联调期视为漏接口 | 联调期必须清零，上线前不得存在 |
| 限流 / 请求过于频繁 | **暂归 409** | 当前 `ErrorCode` 无 429，且已确认口径「不新增自定义码」；用 409 + 明确 `message` 区分。若确实需要专用码，走契约变更流程改本表后再加 | 展示 `message`，退避后重试 |
| 上传分片失败 / 后台任务失败 | 500 | 记录 traceId，任务幂等可重放，不把半成品当成功 | 离线/失败提示 |

### 9.4 抛出、包装与事务规范

- **Service 只抛 `BusinessException`**，不自行 `try/catch` 后转成 `Result.fail`（会造成双层包装与口径分叉），更不吞异常。
- **Controller 不 catch**；异常统一由 `GlobalExceptionHandler` 转成 `Result.fail`，出口唯一。
- **不返回堆栈、内部类名、SQL、表名**给客户端；详细原因只进服务端日志。
- **事务边界在 Service**：下单+清购物车、点赞+计数、投币+扣减等多表写入必须在同一事务；事务内异常整体回滚。**已核查：当前源码全仓 `@Transactional` 为 0 处**，规范已定、实现待补（见 11.3 与 TODO 第 2 项），不得冒充已完成。
- `message` 面向用户可随时改写，**前端只用 `code` 做分支**，不依赖文案字符串。

| 类别 | 端点 | 要求 |
|---|---|---|

- **已知遗留**：现有前端把 `pilipili_token` 存在 `localStorage`（35 处）。按安全规范令牌不应落 localStorage，建议改用 HttpOnly Cookie / 内存态 + 刷新令牌。该项属于「鉴权后期由后端统一做」的范围，本轮未改，**列入上线前加固清单**。

## 11. 写操作状态机与幂等

### 11.1 订单状态机（M13）

```
pending（待支付） ──支付──> paid（已支付） ──发货──> shipped ──收货──> completed
        │                                                    │
        └──取消──> cancelled                            退款──> refunding
```

- 演示期**只实现 `pending / paid / cancelled` 三态**；字段为 VARCHAR 枚举，预留 `shipped / completed / refunding`，禁止用布尔。
- 接口 `POST /api/mall/order/{id}/status`，body `{status}`；非法流转返回 409。
- `POST /mall/order/create`：**total 由后端按 `order_item` 重算**，不采信前端传值；无已选商品返回 409（已实测）；创建后清空已选购物车项，整段操作放事务。
- 库存/限购校验按 `product.limit_per_order`。

### 11.2 其它写操作

| 操作 | 幂等/去重规则 | 事务与校验 |
|---|---|---|
| 加购 `POST /cart` | 以 `product_id` 唯一键去重，重复加购累加 `qty`（`CommerceService` 已实现） | 校验 `productId` 非空、`qty > 0` |
| 改购物车 `PUT /cart/{id}` · 删除 `DELETE /cart/{id}` | 按 id 定位，不存在返回 404 | 单条写入 |
| 发评论 `POST /comment/add` | 每次新建，不做内容去重；`rootId/parentId` 校验归属同一 `vid` | 写入后回填 `comment_count` |
| 楼中楼 `GET /comment/reply/get-more` | 按 `rootId` 返回 `{id,count,replies}` | `id` 必填 |
| 收藏 / 关注 / 点赞 / 投币 | 以 `(uid, target_id)` 唯一键，**重复请求不产生第二条**；投币扣减需校验余额 | 关系表 + 计数在同一事务内更新 |
| 上传 `/upload/init|chunk|merge` | 以 `uploadId` 幂等，重复 chunk 覆盖不重复插入 | 长任务不放在请求处理器内 |

### 11.3 工程要求

## 13. 接口日志与可观测性规范

> **性质：规范已定，实现待落地。** 本轮不改动后端代码（日志/审计实现属于需求方划定的「后期由后端做」范围）。本节是后端接手后实现日志的**唯一依据**，也用于验收。

### 13.1 现状与差距（已核查源码，如实记录）

| 项 | 现状 |
|---|---|
| 配置 | `application.yml` 仅 `logging.level.root=INFO` + 纯文本 console pattern，**无 JSON、无 traceId、无文件滚动、无采样、无脱敏** |
| 代码日志 | 全仓共 **7 条** log 语句：`ApiController` 1 条（只记 `method/path/参数个数`）、`GlobalExceptionHandler` 3 条、`SeedLoader` 1 条、`ContractDispatcher` 2 条 |
| 缺口 | 每请求的 **耗时、结果 code、uid、traceId** 都没有；业务审计、慢请求、脱敏、错误聚合均未实现 |

需求依据：SRS「可观测性：关键业务记录日志，至少包含**请求标识、用户、订单、状态和异常原因**」；SRS 管理端「操作日志至少记录**操作人、时间、对象和结果**」。`交付文档/B站API 设计文档(缺架构图).md` 里的 `traceId`/MDC 写法属 v2 蓝图，**仅作演进参考，不覆盖 v1 契约**。

### 13.2 全接口 access log（每个 `/api/**` 请求必须一条）

用 Filter / Interceptor 在 `finally` 里打点，保证**异常路径也有日志**。字段固定，结构化输出（单行 JSON）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `traceId` | string | 全链路标识，见 13.6；三处日志（access / 业务 / 异常）必须一致 |
| `ts` | ISO8601 | 请求到达时间 |
| `method` · `path` | string | HTTP 方法与去掉 `/api` 后的路径 |
| `route` | string | 实际命中的处理器 key（如 `GET /mall/product/p1` 的模式名），便于统计 501 与慢接口 |
| `uid` | long | 取自 `JwtInterceptor.ATTR_UID`；匿名记 0，不打用户名 |
| `code` | int | **body 里的业务 code**，不是 HTTP 状态 |
| `httpStatus` | int | 恒 200（见 9.1），异常时由容器决定 |
| `durationMs` | int | 耗时；超过阈值升级为 WARN |
| `clientIp` · `userAgent` | string | 用于审计与风控 |
| `reqSize` · `respSize` | int | 字节数 |
| `errorType` · `message` | string | 仅失败时填；`message` 必须脱敏后写入 |

**禁止**把 request/response body 全文打进 access log（含密码、评论正文、私聊内容、token）。

### 13.3 日志级别约定

| 级别 | 用途 | 生产 |
|---|---|---|
| DEBUG | 参数明细、SQL 绑定值（**脱敏后**）、契约命中细节 | 关闭 |
| INFO | 每条 access log、服务启动、契约注册数、种子导入数 | 保留 |
| WARN | 业务异常 / 4xx / 501 未登记 / 慢请求（>500ms，阈值可配）/ 幂等重放命中 | 保留 |
| ERROR | 未捕获异常、DB 故障、事务回滚、外部依赖不可用（**带堆栈 + traceId**） | 保留 + 告警 |

### 13.4 脱敏清单（强制）

| 字段 | 规则 |
|---|---|
| `password` · `code`（验证码）· `Authorization` / `pilipili_token` | **完全不记录**，日志里只允许出现「已提供/缺失」 |
| `phone` | `138****8000` |
| `email` | `a***@example.com` |
| `address` · `idCard` · 真实姓名 | 只记长度或哈希前缀 |
| 评论 / 私聊内容 | 只记长度与内容 id，不记正文 |
| 请求 body | 默认不记；确需排查时仅记字段名白名单 |

验收口径：日志文件中对 `password`、完整手机号、完整 JWT 的全文命中数必须为 **0**。

### 13.5 审计日志（写操作必记，独立于 access log）

**范围**：所有 `POST / PUT / DELETE / PATCH`、登录/登出/改密、以及管理端 `/admin/*` 全部端点。

| 字段 | 说明 |
|---|---|
| `traceId` · `ts` | 与 access log 对齐 |
| `actorUid` · `actorRole` | 操作人；**以 token 内 uid 为准**，不信请求参数 |
| `action` | 端点（如 `POST /mall/order/create`） |
| `targetType` · `targetId` | 被操作对象（订单/视频/评论/用户） |
| `before` · `after` | 状态/金额摘要（订单场景必填：status 流转前后、`total`、`orderId`） |
| `result` · `reason` | 业务 code 与失败原因（脱敏） |
| `ip` | 来源 |

要求：**单独持久化**（建议 `operation_log` 表），不能只打 console；业务异常时也要落「失败」记录，不得被事务回滚一起抹掉（可用独立事务/异步落库）；满足 SRS「至少记录操作人、时间、对象和结果」。`/admin/*` 额外要求参数脱敏 + 角色校验（第 10 节 RBAC）。

### 13.6 traceId 全链路

1. 入口 Filter 读取上游 `X-Request-Id`，没有则生成；放入 MDC，并**回写到响应头 `X-Request-Id`**。
2. `ApiController` 的 access log、`GlobalExceptionHandler` 的异常日志、审计日志、501 WARN **共用同一 traceId**。
3. 跨线程/异步任务（上传合并、结算后台任务）必须显式传递 MDC，不能丢。
4. 前端 `request.js` 从响应头取 `X-Request-Id`，附到开发态 `console.warn` 与后续错误上报；用户反馈问题时凭此 ID 可串起完整链路。

### 13.7 分级矩阵（按端点类别）

| 端点类别 | access log | 审计日志 | 额外要求 |
|---|---|---|---|
| 公开浏览 / 搜索 / 详情 GET | INFO（可按比例采样降量） | 不需要 | 慢请求 WARN |
| 商城 / 购物车 / 订单 读写 | INFO，失败 WARN | **必须** | 订单状态与金额变更记 before/after；>500ms WARN |
| 登录 / 注册 / 改密 / 验证码 | INFO | **必须** | 密码、验证码绝不入日志 |
| 消息 / 私聊 / 评论 | INFO | 元数据（不记正文） | 只记内容 id 与长度 |
| 管理端 `/admin/*` | INFO | **完整 + 参数脱敏** | 角色校验结果一并记录 |
| `/api/health` | DEBUG 或采样 | 不需要 | 避免健康检查刷屏 |
| **未登记 `code:501`** | **WARN 必记** | 不需要 | 记 path + traceId，作为迁移看板数据源 |

### 13.8 实施顺序（后端排期建议）

1. `RequestIdFilter`：生成/透传 traceId + MDC + 响应头（其余日志的前置条件）。
2. `AccessLogInterceptor`：`finally` 打点，补齐 duration / code / uid / route。
3. `logback-spring.xml`：console 与文件双输出、JSON encoder、按天滚动 + 保留策略、生产关 DEBUG。
4. `operation_log` 表 + AOP/注解落审计（写操作零遗漏）。
5. 慢请求、错误率、501 计数看板与告警。
6. 压测确认异步 appender 不影响吞吐。

### 13.9 验收口径

- 任取一个请求，能用 `traceId` 串起 **access + 业务/审计 + 异常** 三段日志。
- 密码 / 验证码 / 完整 JWT / 完整手机号在日志中全文命中 **0**。
- 每个写操作都能查到操作人、时间、对象、结果。
- `code:501` 有日志可统计，上线前清零。
- 慢请求与 5xx 有独立告警，不是靠翻 console 发现。

## 14. 层与层传输规范

> 7.1 只覆盖「前端 ↔ 后端」的 HTTP 传输；本节定义**后端内部各层之间**怎么传、谁负责转换、哪些事禁止越层。层级划分取自现有源码，不是重新设计架构。

### 14.1 现有调用链（照代码）

```
HTTP 请求
  ↓  ApiPrefixFilter      补 /api 前缀，兼容 vue.config.js 的 pathRewrite；不碰业务参数
  ↓  ApiController        @RequestMapping("/api/**")：解析 query + JSON body、取 uid、组装 ApiContext
  ↓  ContractDispatcher   精确端点 ex() → 路径模式 pat() → contract_seed 兜底；都无则抛 501
  ↓  XxxService           业务规则、SQL 编排、事务；抛 BusinessException；返回纯数据或 Result
  ↓  DataRepository       JdbcTemplate；统一把 DB 的 snake_case 列转成 camelCase
  ↓  SeedRepository       契约种子静态样例（待逐步迁移）
  ↓  MySQL (18 张表)

异常旁路：任意层抛 BusinessException / 未捕获异常 → GlobalExceptionHandler → Result.fail
响应出口：Result.ok / Result.fail → JSON {code, message, data}（HTTP 恒 200，见 9.1）
```

### 14.2 各层职责与禁止事项

| 层 | 允许 | **禁止** |
|---|---|---|
| `Filter` | 前缀兼容、traceId/MDC、access log 打点 | 改写业务参数、做业务判断、吞异常 |
| `Controller` | HTTP 解析、组装 `ApiContext`、返回 `Result` | **写 SQL**、业务分支、`try/catch` 后手工拼错误响应、认识 `JdbcTemplate` |
| `ApiContext` | 唯一的层间入参载体：`method / path / input / uid / vars` | Service 依赖 `HttpServletRequest`、`HttpSession`、`ResponseEntity` |
| `ContractDispatcher` | 只做路由与兜底查找 | 写业务逻辑、吞异常、改响应字段 |
| `Service` | 业务与事务、`BusinessException`、返回 `Map/List/标量/Result` | 直接拼 HTTP 响应、返回未经 `toCamel` 的数据库原始行 |
| `Repository` | SQL + 列名转换 | 认识 HTTP / `Result` / token；**身份语义由 Service 传 uid 进来**，Repository 不自行解析用户 |
| 前端 `request.js` | 解包到 `response`，开发态对 `code!=200` 留痕 | 在页面里解析 HTTP 状态码、按 `message` 文案做分支 |

### 14.3 层间载体与出参形状

- **入参**：`ApiContext`。`input` 只读使用；路径变量由 Dispatcher 通过 `putVar()` 写入，Service 用 `var()` 取。取值统一走 `str / lng / integer / bool` 带默认值方法，**不在 Service 里重复解析 `Map`**。
- **出参**：`Result<T>` 是 Controller 边界的唯一出口，`T` 为 `Map<String,Object>`、`List<Map<String,Object>>`、标量或 `null`。
- 形状约定：列表 `{list, total, page, size}`；单条 `{...}`；无内容 `data:null`；**失败一律 `data:null`**，禁止半填充。
- 禁止在层间传递 `HttpServletRequest`、`ResultSet`、`JdbcTemplate`、`Optional`（`Optional` 仅限 Repository 内部）。
- `ContractDispatcher.dispatch()` 已兼容 Service 返回纯数据或已包装的 `Result`（`out instanceof Result`）。**新代码建议统一返回纯数据由 Controller 包装**，避免两种风格长期并存。

### 14.4 命名与类型转换（一处转换，全链路不改字段）

- 数据库列 `snake_case` → 接口字段 `camelCase`，**只在 `DataRepository.toCamel()` 一处完成**；Service 与前端不得二次改名。
- `contract_seed` 里的静态样例字段名同样是 camelCase，**迁移到真实 SQL 时不得顺手改名**，否则前端立即分叉。
- 已确认硬约定（8.1）在层间同样不得变形：金额「元」`DECIMAL(10,2)` 不转分；`vid/uid` 为 BIGINT 数字；`sold` 为绝对整数（展示层才格式化成「2.3万」）；时间由服务端格式化；订单状态为字符串枚举。
- 类型不一致时**以后端为准修前端适配**，不为迁就前端旧 mock 改契约；任何字段变更先改本表，再改代码，最后重跑生成器。

### 14.5 响应包装与异常出口唯一

- 成功：`Result.ok(data)` / `Result.ok(data, message)`；失败：`Result.fail(ErrorCode)` / `Result.fail(code, message)`。
- HTTP 状态恒 200（9.1）；`GlobalExceptionHandler` 是**唯一**异常转响应出口，Controller 不另设 catch（9.4）。
- `message` 可改，`code` 稳定；前端只用 `code` 分支。

### 14.6 事务边界

- 事务标注在 **Service 方法**（`@Transactional`），不放 Controller、不放 Repository。
- 多表写入（下单+清购物车、点赞+计数、投币+扣减、关注+粉丝数）必须同一事务；异常整体回滚并返回 500，禁止部分成功。
- **已核查：当前源码 `@Transactional` 为 0 处**。规范已定、实现待补（11.3 / TODO 第 2 项），后端迁移 `POST /mall/order/create` 等写操作时优先补上。

### 14.7 前端解包约定（避免前后端各写一套）

```
get/post/put/del  →  axios response
页面              →  res.data.code === 200 ? res.data.data : 按第 9 节处理
```

- 不解析 HTTP 状态码；不依赖 `message` 文案；`code!=200` 由 `request.js` 拦截器开发态 `console.warn` 留痕（已实现），生产统一友好提示（待办）。
- 前端不做字段改名、不做单位换算、不做时间格式化之外的业务计算（`total` 由后端重算，见 11.1）。

### 14.8 新增端点自检清单

- [ ] `ContractDispatcher` 注册 `ex()` / `pat()` → Service 方法 → Repository SQL，**三层各归其位**，无越层
